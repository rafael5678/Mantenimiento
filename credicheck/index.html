02 · BLOQUE 1 · REGLAS DE NEGOCIO & FRONTERAS reglas_credito.py

El Negocio, Reglas de Decisión & Fronteras Numéricas

La API evalúa tres entradas cuantitativas (score 300–850, ingresos ≥ 0 y monto 500–100.000) y produce una de tres decisiones deterministas: APROBADO, APROBADO_PARCIAL o RECHAZADO.

Pipeline de Decisión en 5 Pasos

Lógica Pura
PasoCondición EvaluadaResultado / Decisión
1. TiposScore entero (no bool), ingresos/monto numéricosTypeError → API responde 422
1. Dominio300 ≤ score ≤ 850 · ingresos ≥ 0 · 500 ≤ monto ≤ 100.000ValueError → API responde 400
2. Scorescore < 600RECHAZADO · SCORE_INSUFICIENTE
3. Ingresosingresos < 2.000RECHAZADO · INGRESOS_INSUFICIENTES
4. CapacidadMonto máximo = ingresos × multiplicador banda600–699: ×3 | 700–799: ×5 | 800–850: ×8
5. Aprobaciónmonto ≤ monto_maximo vs. monto > monto_maximoAPROBADO vs. APROBADO_PARCIAL (ajusta a máx)

Frontera Crítica: El Centavo

Score 700 / Ingresos 2.000

Banda 700–799 (×5). Monto máximo = 2.000 × 5 = 10.000,00:

Monto: 10.000,00 → APROBADO (Cumple requisitos) Monto: 10.000,01 → APROBADO_PARCIAL (10.000,00)
  • Error off-by-one: Si el desarrollador escribe <= 600 en vez de < 600, un cliente con 600 es rechazado ilegalmente.
  • Diseño BVA: 18 fronteras numéricas exactas testeadas en milisegundos sin tocar la base de datos ni la red.

05 · BLOQUE 2 · CALIDAD & CONTRATOS DE API Expositor: Rafael · JSON Schema

Pruebas de Contrato de API con JSON Schema en Docker

Verificación estricta en el "punto dulce" de la pirámide: pruebas HTTP reales desde el contenedor test-runner contra la API en ejecución para garantizar que ningún cambio de backend rompa a los clientes.

Aislamiento en Docker

test-runner
docker compose --profile pruebas \ run --rm --build test-runner

Docker Compose aguarda el healthcheck de la API y el contenedor lanza 17 pruebas HTTP hacia http://api:8000.

Solución IPv6: En Windows, localhost causa timeout de 2 s por resolución IPv6; las pruebas reescriben a 127.0.0.1.

4 Niveles de Aserción

_afirmar_niveles()
  • Nivel 1 (Petición): Envío real de payload por HTTP.
  • Nivel 2 (Código de Estado): Comprobación estricta de 200, 201, 400, 404 o 422.
  • Nivel 3 (Cabeceras & Tiempo): Content-Type: application/json y latencia < 1 s (creación) o < 500 ms (consulta).
  • Nivel 4 (Esquema JSON): Validación completa contra JSON Schema Draft 7 con jsonschema.validate.

Esquema de Evaluación

12 Campos Requeridos
  • Integridad absoluta: Exige id, solicitante, score, ingresos, monto_solicitado, decision, motivo, monto_maximo, monto_aprobado, comprobante, fecha y version_api.
  • additionalProperties: false: Prohíbe campos fantasma.
  • enum: Restringe decisiones y motivos válidos.
  • pattern: Valida formato UUID v4 y fecha UTC ISO 8601.

06 · BLOQUE 2 · CI & DEVSECOPS Expositor: Rafael · ci.yml

Integración Continua (CI) & Estrategia sin Conflictos

Pipeline de integración continua en GitHub Actions con acciones fijadas por SHA completo, arquitectura de jobs paralelos y gobernanza colaborativa por dominios.

Flujo de Jobs en ci.yml

DevSecOps
pruebas-unitarias (genera coverage.xml) ├──► pruebas-contrato (Docker Compose test-runner) ├──► pruebas-integracion (LocalStack S3/SQS) └──► analisis-sonarcloud (Quality Gate "Sonar way")
  • Fijación por SHA: Todas las acciones de terceros usan commit SHA completo (ej. actions/checkout@11bd719... # v4.2.2) para prevenir ataques a la cadena de suministro (*supply chain*).
  • Status checks obligatorios: La rama main se blinda; si cualquiera de los cuatro jobs falla, el Pull Request no puede fusionarse.

Estrategia Colaborativa

CODEOWNERS
  • Ramas por Dominio: feature/backend-frontend, feature/calidad-ci, feature/infra-cd.
  • Propiedad Clara: Archivo .github/CODEOWNERS asigna la responsabilidad exclusiva de cada módulo.
  • Congelación Temprana: Los contratos (interfaces del repositorio y schemas) se acordaron el primer día.
  • Resultado: 4 Pull Requests fusionados con merge commit con 0 conflictos.

08 · BLOQUE 2 · PRUEBAS DE CARGA & RENDIMIENTO Expositor: Rafael · Locust 2.31.8

Pruebas de Carga con Locust, Ley de Little & Punto de Quiebre

Simulación no funcional con carga/locustfile.py modelando usuarios concurrentes (AnalistaCredito) con think time de 1–3 s para identificar la capacidad máxima y el cuello de botella.

Resultados Experimentales Medidos

Noviembre 2026
UsuariosRPS Teórico (N/2)RPS RealMedianap95Diagnóstico
10050 RPS50 RPS8 ms16 msZona Sana: Holgura total (0% fallos)
500250 RPS~207–230~360 ms600–860 msPunto de Quiebre: p95 > 800 ms
1.200600 RPS~240–260~3.000 ms3.900–4.800 msSaturación: Peticiones en cola

Ley de Little ($N = \text{RPS} \times (R + Z)$): Con 100 usuarios y 2 s de espera, $100 / 2 = 50$ RPS exactos medidos. Con 1.200 usuarios y techo de ~250 RPS, cada ciclo dura $1.200 / 250 = 4,8$ s (2 s think time + 2,8 s latencia real).

Cuello de Botella & QG #3

Diagnóstico Técnico
  • Quality Gate #3: El proceso termina con exit 1 si fallos > 1% o p95 > 800 ms.
  • Cuello de botella: Un único proceso de uvicorn escribiendo de manera síncrona en LocalStack S3 y SQS.
  • ¿Por qué 0% fallos en saturación? La API no rechaza conexiones, las encola. Locust espera sin timeout; un usuario humano consideraría fallida una espera de 4 segundos.
  • Propuesta perfectiva: Desplegar con --workers 4 y balanceador de carga.

Infraestructura como Código (IaC) Idempotente en LocalStack

Aprovisionamiento declarativo y versionado en Git que emula la nube de AWS en LocalStack 3.8.1 (puerto 4566), eliminando por completo la deriva de configuración (configuration drift).

Bucket S3 Seguro

credicheck-evaluaciones
  • Versionado Activo: Preserva el historial inmutable de comprobantes JSON de crédito.
  • Cifrado AES256: Cifrado en reposo del lado del servidor habilitado por defecto.
  • Block Public Access: Restricción total de ACLs y políticas públicas para cumplimiento regulatorio.

Colas SQS & DLQ

credicheck-eventos
  • Cola Principal: Recepción asíncrona de eventos de evaluación generados por la API.
  • Dead-Letter Queue (DLQ): Cola credicheck-eventos-dlq que retiene durante 14 días mensajes fallidos.
  • Redrive Policy: Enrutamiento automático a la DLQ tras exactamente 3 reintentos fallidos.

Principio de Idempotencia

init_infra.py

El script verifica antes de crear mediante head_bucket y get_queue_url:

1ra ejecución: CREADO / CREADA 2da ejecución: YA EXISTE (solo sincroniza)

Arranque ordenado: En docker-compose.yml, la API espera la condición service_completed_successfully del contenedor infra-init.

11 · BLOQUE 3 · DESPLIEGUE CONTINUO & TELEMETRÍA Expositor: Saray · deploy.py

Despliegue Continuo (CD), Rollback Automático & Mensajería

Estrategia Blue/Green simplificada orquestada por deploy/deploy.py. Si la versión candidata falla en staging, producción jamás se interrumpe y el equipo recibe alertas en tiempo real por Telegram.

Flujo Blue/Green Staging

Puertos 8001 / 8002
  • 1. Candidata en Staging (:8001): Despliega el commit exacto validado por la CI.
  • 2. 4 Smoke Tests: Valida /health con versión esperada, /reglas, creación POST con guardado en S3 y lectura GET.
  • 3. Promoción (:8002): Si pasa, reemplaza producción y etiqueta credicheck-api:estable.

Rollback Automático

Tolerancia a Fallos

Si staging arroja ConnectionError o HTTP 500:

  • Producción Intacta: Se destruye el contenedor de staging sin tocar el puerto 8002.
  • Alerta Inmediata: Telegram dispara ⚠️ ROLLBACK AUTOMÁTICO.
  • Caso Demo (demo-puerto): Simulamos un cambio erróneo de puerto 8000 → 8080 en Dockerfile; staging no respondió y producción retuvo la versión sana.

Mensajería Asíncrona

SQS → Telegram
  • Desacoplamiento: La API responde en milisegundos tras publicar el evento en SQS.
  • Consumidor en background: deploy/consumidor_eventos.py procesa la cola y notifica evaluaciones aprobadas.
  • Seguridad de Secretos: Tokens de Telegram inyectados exclusivamente vía GitHub Secrets y .env local protegido.
